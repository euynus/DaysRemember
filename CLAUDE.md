# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project shape

Native SwiftUI iOS 26+ app, built in the Swift 6 language mode — Chinese-language anniversary / countdown ("时光 · Days Remember"). The current UI (the 柔彩便当 redesign) uses three native tabs, a pastel card feed split into 将至 and 已过, a monthly agenda, and shared app/widget layouts. `_design/days-remember/` preserves the historical prototype, not the current visual specification. Two targets: the main app (`DaysRemember`, bundle ID `dev.gooday.days`) and a WidgetKit extension (`DaysRememberWidget`, `dev.gooday.days.widget`).

## Build & run

The Xcode project is **generated** from `project.yml` by [XcodeGen](https://github.com/yonaskolb/XcodeGen). `DaysRemember.xcodeproj/` is gitignored — never edit it directly. After any change to `project.yml`, file structure, or entitlements, regenerate.

```sh
brew install xcodegen          # one-time
xcodegen generate              # rewrites DaysRemember.xcodeproj
open DaysRemember.xcodeproj
```

CLI build (no Xcode UI). The simulator UDID is whichever iPhone 17/Pro is booted; query with `xcrun simctl list devices available`.

```sh
xcodebuild -project DaysRemember.xcodeproj -scheme DaysRemember \
  -destination 'platform=iOS Simulator,id=<UDID>' \
  -derivedDataPath /tmp/dr-dd build
```

`bash scripts/archive.sh` archives for the App Store, exports the IPA with `scripts/ExportOptions.plist` and checks it (production `aps-environment` and iCloud environment, matching app and widget versions, the App Group, an opaque marketing icon); `--upload` then sends it to App Store Connect and `--unsigned` only checks the device build, as CI does. It needs `DEVELOPMENT_TEAM` in `project.yml` (or `TEAM_ID=`) and a clean tree, and numbers the build by commit count (`BUILD_NUMBER=` overrides); both Info.plists read `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` from `project.yml`.

Keep simulator ad-hoc signing enabled as configured in `project.yml`; App Group and widget integration require it. Use `bash scripts/ci.sh` for the full CI suite and Release build on a disposable simulator; it keeps each run's logs, coverage and result bundle in `build/ci/` and removes its DerivedData. The UI tests are written against an iPhone 17's screen, so unless `IOS_RUNTIME` / `IOS_DEVICE_TYPE` name them, it takes the newest iOS runtime that still simulates an iPhone 17 (a newer one can drop it), and never the folding iPhone Duo, whose inner display lays the app out like an iPad. It doesn't collect test diagnostics: on Xcode 27 the simulator could keep xcodebuild waiting ten minutes for them after a passing run. A failing test is retried up to twice (`-retry-tests-on-failure`), and when GitHub's runner can't start the UI test runner ("Timed out while loading Accessibility") and nothing else failed, the UI tests run once more. A test that goes past its 300-second allowance isn't retried, since the runner restarts and moves on; XCTest occasionally waits a minute at every step for animations that never report complete ("App animations complete notification not received") or stalls launching the app, so when only such tests failed, they alone run once more (`-only-testing`). Each further run's result bundle is merged into `Tests.xcresult`, and `scripts/ci-tests/ci.test.sh` checks all of this against stub tools. UI tests reveal elements with `XCUIApplication.scrollUntilHittable`, short drags that don't carry a lazy grid's cell out of the accessibility tree, and tap the document picker with `tapWhereItIs`, which a vanishing element can't fail. The `DaysRememberCI` scheme excludes only the manually configured Home Screen widget test. Single test class on a dedicated test device: `xcodebuild ... test -only-testing:DaysRememberTests/LunarTests`. UI fixtures reset their simulator's library and start from the system language (a relaunch without a fixture argument keeps the language its test chose), so never use a simulator containing user data.

When SourceKit reports "Cannot find Theme / Day / DayInfo in scope" on a single file, that is **file-isolation** — there's no per-file build context outside the project. Run `xcodegen generate` and rely on `xcodebuild` for ground truth.

## Debug launch arguments

The app reads the following from `ProcessInfo.processInfo.arguments` / env (defined in `DebugLaunch.swift`):

```sh
# Pin "today" to 2026-04-23 to match the prototype's hard-coded countdowns
SIMCTL_CHILD_DR_PIN_TODAY=1 xcrun simctl launch <UDID> dev.gooday.days

# Land on a specific tab
xcrun simctl launch <UDID> dev.gooday.days --tab calendar          # home | calendar | me (categories / notifications / settings open me)
xcrun simctl launch <UDID> dev.gooday.days --face past             # home opens on 已过 (default upcoming)

# Bypass the tab shell entirely and open one screen
xcrun simctl launch <UDID> dev.gooday.days --screen detail --day wedding
xcrun simctl launch <UDID> dev.gooday.days --screen onboarding
# also: --screen add | share | widgets | settings | sync-choice
```

`--day` accepts any sample id from `Models/SampleData.swift` (`wedding`, `baby`, `birthday`, `midautumn`, `japan`, `kaoyan`, `firstmet`, `work`, `dog`, `moved`).

## Architecture

### Data flow

`DayStore` (`Store/DayStore.swift`) is the single `@MainActor @Observable` source of truth for both `days: [Day]` and `categories: [CategoryDefinition]`. Categories and active-day metadata use `categories.v1` / `days.v2` in **shared UserDefaults** via `SharedStorage.defaults` (App Group `group.dev.gooday.days`). `PhotoFileStore` supplies the local Codable context that writes photos to content-addressed App Group files, deleted once no stored record (active, deleted or replaced days, or the recovery, migration and restore journals) refers to them; plain Codable encoders keep inline photos for portable backups. Recently deleted days (`deletedDays.v1`) and replaced sync versions (`syncConflicts.v1`) use the same file-backed encoding and expire after `DayStore.retention` (30 days); older inline records still decode. A restore or a cloud update replaces the recovery copy (恢复上一次本机副本) only through `applyBackup`'s `beforeWriting`, after every fallible photo write, so one that fails keeps the copy it had. `permanentlyDeleteDay` takes the day out of 最近删除, 同步保留版本, the recovery copy and the pre-migration backup; 清除本机内部副本 (`clearInternalCopies`) deletes the recovery copy, the pre-migration backup, the raw copy a restore replaced and checkpoints sync set aside, then the photos only they used. Custom test stores can inject a photo directory or omit it for inline-only persistence, which keeps days under `days.v1`.

`DayStore.days.didSet` chains three side effects in order: `save()` → `rescheduleNotifications()` → `reloadWidgetTimelines()`. So *any* mutation — `add`, `update`, `delete`, `resetToSamples` — automatically persists, re-syncs `UNUserNotificationCenter`, and pokes `WidgetCenter`. `categories.didSet` persists and then reloads widget timelines, since widget cards take a custom category's colour (a colour-only edit changes no day); notifications don't depend on categories. Tests replace `DayStore.reloadWidgets` to count reloads. The day editor keeps its working copy in a `DayDraft` (the dirty check, the cover rules and the day it saves; `CoverPhotoImport` loads a picked photo), both tested without a view, and saves with `update(_:editedFrom:)`, passing the day as it opened: a change that synced in meanwhile survives where the edit left that part alone (`DayStore.merging` moves the date and its calendar, a photo and its framing, a category and its label, and the reminders as groups), and where both changed the same group the edit wins and the replaced version goes to 同步保留版本. `add(_:)` and `update(_:)` route through `normalized(_:)`, which reconciles the day's `categoryID` / `categoryLabel` against the current category list and clamps `coverFocusX/Y` into `[0, 1]`.

`AppSettings` (`Store/AppSettings.swift`) is a separate `@Observable` class backed by `UserDefaults.standard` (onboarding flag, per-offset reminders, daily `notificationHour`/`notificationMinute`, plus `momentsEnabled` (每日问候 — a repeating greeting at `greetingHour`/`greetingMinute`, default 08:00) and `memoryEnabled` (时光回忆 — a yearly "想起这一天" for past days); both are scheduled in `NotificationManager.sync`). Quiet hours were removed: `AppSettingsSnapshot` still encodes `quietHours: false`, and decodes a missing greeting time as 08:00, for older devices. It's wired to `DayStore` via `store.settings = settings` in `DaysRememberApp.swift`'s `.task` — that pattern avoids a circular dependency between the two objects.

### iCloud sync

Days and categories sync through `Store/CloudLibrarySync.swift`: native `CKSyncEngine`, a private custom zone in `iCloud.dev.gooday.days`, separate day/category records and `CKAsset` photos, with record mapping in `CloudLibraryRecord.swift` and the locally checkpointed `CloudLibraryState` in `CloudLibraryState.swift`. `DayStore.persist` forwards each saved snapshot through `CloudLibrarySync.shared.updateLocal`; remote changes arrive in `DayStore.applyCloudUpdate`, which merges by record ID and keeps every replaced local version as a `SyncConflict` (restorable in 数据与同步). Automated and simulator launches do not connect to CloudKit.

Each device chooses whether to sync. `AppSettings.syncChoice` (`sync.choice.v1` in standard defaults, never in the synced settings snapshot) stays nil, and nothing reaches iCloud, until onboarding's last step (`SyncChoiceView`) or, on a device that synced before the choice existed, a one-time gate in `RootGate` (automated launches skip it). `CloudSyncControl` applies the choice to CloudKit, settings KVS and push registration: `resume` at launch, `choose` from onboarding, the gate and 数据与同步's toggle; onboarding chooses before it finishes, so `RootTabView` sees the first download pending. Turning sync off stops the engine and deletes the checkpoint and the copies of days and photos it kept (`CloudLibrarySync.stop`, which gives itself a fresh `PhotoFileStore`, since one that remembers deleted files takes them for damaged ones); turning it on again starts from an empty checkpoint, as 重置同步状态 does. 删除 iCloud 中的数据 (`CloudSyncControl.deleteCloudData`) turns sync off, deletes the zone and removes every KVS key; other devices see the zone deleted, keep their days and pause.

A fetched record this version can't read (a newer `schemaVersion`, an enum value or record type it doesn't know, a failed validation) is set aside by `CloudLibraryState.receiveIfReadable` instead of failing its batch, since a failed batch never advances the change token and the record would stop every later sync; a photo still downloading fails as before. Set-aside records are listed in the checkpoint's `unreadable` with the app version that tried, counted in 数据与同步, and keep the local version they replaced; an edit to one isn't sent (a deletion is). The first engine of a different app version forgets the change token (`retryUnreadable`) so the whole zone is fetched again; an edit made meanwhile is then merged onto the server version, as below. The version is `CFBundleShortVersionString (CFBundleVersion)`, so only archived builds tell one another apart. Never make `Day` decoding fall back for an unknown value instead: the older version would upload that fallback over the newer value.

Each checkpoint entry keeps `base`, the server version its `serverFingerprint` names (set on receive, and from `sentValue` when a save is acknowledged). When the server changes a day that has an unsent local edit, on fetch or as a rejected save, `CloudLibraryState.merging` runs `DayStore.merging` with `editWins: false`: groups only the edit changed survive and go up again, the server wins groups both changed, and then the local version is kept in 同步保留版本. Older checkpoints have no base and fall back to the server's version. `acknowledgeRemoteUpdate` leaves a delivered value dirty when it isn't what the server holds. An `unknownItem` save failure deletes a record the server held but resends one it never held (`receiveMissing`).

`start` checks the first local snapshot against the checkpoint (`CloudLibraryState.missingMost`): a library that comes up without most of the days iCloud holds (any, if it's empty) was more likely unreadable than emptied on purpose, so those records are kept out of inferred deletions until 数据与同步's 从 iCloud 恢复这些日子 (`restoreMissing`, delivered as a remote update) or 在所有设备上删除 (`confirmMissingDeletions`); other changes keep syncing. Restores go through `updateLocal` directly and aren't held. Sync starts again by itself (`resumeIfNeeded`, on returning to the foreground and on `.CKAccountChanged`) when it has no engine and stopped on a failure, an unavailable account or before it began; a running engine retries on its own. A checkpoint that can't be read is set aside as `*.unreadable.json` by 重置同步状态 (`DayStore.resetCloudSync`). 我的's 数据与同步 row shows `attentionSummary`, and while a new device's first fetch is pending (`isFirstDownloadPending`) the empty feed says the library is downloading, and the first day's editor that onboarding opens waits until it has brought nothing (`RootTabView.firstDayAfterDownload`).

Only settings still use `Store/ICloudSyncStore.swift`: an `NSUbiquitousKeyValueStore` envelope `{ updatedAt, deviceID, value }` under `icloud.settings.v1`, last-writer-wins on `updatedAt`, with the remote timestamp mirrored at `icloud.localTimestamp.<key>`. Applying a remote snapshot suppresses the resulting push and cancels any pending debounced one. The KVS entitlement lives on `DaysRemember.entitlements` only — the widget reads through shared `UserDefaults`.

### Navigation shell

`RootTabView` uses SwiftUI `TabView` with three labelled tabs: 日子, 日历 and 我的. Each retains a `NavigationStack` and `NavigationPath`; detail destinations are typed as `DayRoute` (a day ID — `DetailView` reads the live record and closes itself when a sync deletes the day), category destinations as `CategoryRoute`, and 我的's reminder screen as `MeRoute`. Search is a header button on 日子 (`home.search`); it predates the iOS 26 target, under which `Tab(role: .search)` is now available. Root screens supply their own headers and hide the system navigation bar; pushed screens (day detail, category day list, reminders) keep it, because a hidden bar disables the interactive edge swipe, and put their actions in toolbar items. `HomeView` switches between two faces: `UpcomingFace` 将至 (`!DayInfo.isPast`, with a paging hero of the five nearest days, a week-long `RecentOccurrence` banner for a recurring day that just passed, and a two-column `DayGrid`) and `PastFace` 已过 (past one-time days, with a hero for the soonest `Milestone` — every 100 days up to 1,000, every 500 after, or a whole year); the pager's page stays in `HomeView` so it survives a face switch. `MeView` holds the library stats (`MeStats`), the category grid (`MeCategoryGrid` of `CategoryTile`s), a link to `NotificationsView`, and the widget, data, language and about rows; `SettingsView` is now only a namespace for `siteURL` and `version`. Native tab safe areas replace the old floating-bar padding. Category lists derive their contents from the live store rather than keeping a stale array. The editor for an existing day is presented by `dayEditorHost()` at the tab root, which rows, the hero card and details reach through `\.editDay`: a sheet on one of those would close with it, or follow the hero card to another day. Category editors are presented the same way by `categoryEditorHost()` through `\.editCategory`: a sheet inside 我的 would be rebuilt, losing its draft, when a link switches to 日子.

Two layout invariants every screen must follow:

1. The outer `VStack` ends with `.frame(maxWidth: .infinity, maxHeight: .infinity, alignment: .top)` so it claims the full vertical area instead of intrinsic sizing.
2. Don't use `Image(systemName: "...").opacity(0)` as a layout-balance placeholder — without an explicit `.font()` the system Image's intrinsic size inflates the row and floats the screen toward the middle. Use `Color.clear.frame(width: 18, height: 18)` instead.

### Theme

The app uses the 柔彩便当 style: a light neutral canvas, each day on a pastel card in its category colour (`CategoryColorToken.soft`, with `.color` for text and marks on it), ink headings and ink pill actions, heavy rounded numerals, and flat outline-free cover illustrations drawn straight onto the card. Count-up days and memories use the lavender `Theme.memory` / `Theme.memoryInk`. User-selected photos retain their original rendering. Avoid heavy shadows, nested cards, and decorative illustration overlays. It remains **light-mode only** via `Info.plist` and `.preferredColorScheme(.light)`. Dynamic Type is supported; fixed seven-column date cells, the category editor's five-column icon grid and the editor action bar cap scaling at XXXL. Printed share previews and fixed-size widgets constrain their internal text scale independently of app controls.

`Theme/Tokens.swift` defines colors, scalable Inter/system text, and heavy SF Rounded countdown numerals: `.numberFont(_:)` (`Theme/NumberFont.swift`) scales them with the environment's Dynamic Type size (so `.dynamicTypeSize(...)` caps apply), and `Theme.number` is the fixed-size font for widgets and share images. Meaningful SF Symbols take `Theme.symbol(_:weight:)`, which follows Dynamic Type at the given size for the default text size; `.font(.system(size:))` is left only for decoration in fixed-size tiles. The five persisted `CategoryColorToken` names (`rose`/`amber`/`dusty`/`sage`/`terracotta`) remain stable. Non-category meanings use semantic tokens (`Theme.solarTerm`, `Theme.danger`, `Theme.coverPaper`), never category colors. XcodeGen flattens bundled resources, so `UIAppFonts` must use bare filenames rather than `Fonts/` paths. Inter is under the SIL Open Font License, so `Fonts/OFL.txt` ships beside it in the app and the widget.

Reusable navigation, filters, metadata, grouped rows, native pickers, and toggles live in `Views/Components/`, one type per file (`NavHeader`, `Chip`, `MetaRow` with its `MetaItem`, `CardList`, `SegPicker`, `ToggleCell`, …). Category icons use SF Symbols; `CategoryDefinition.symbolName` maps legacy stored sticker names to their equivalent symbols.

`PhotoStyle` keeps existing raw identifiers but maps them to the twelve flat illustrations in `PhotoStyle.pickerOptions` through `assetName` — vector `Flat*` assets, written into both the app and widget catalogs and the site's `docs/assets/covers/` by `python3 scripts/flat-covers.py`. The editor compares asset names when highlighting a preset so legacy aliases remain selected. `PhotoTile` renders `Day.photoData` first, using `coverFocusX/Y`, then falls back to the preset (also for a photo that can't be decoded), fitted with a `PhotoTile.presetInset` margin on `Theme.coverPaper`; user photos fill and crop as before. A new day's cover follows its system category (`PhotoStyle.defaultCover(forCategoryID:)`) until a template or photo is picked. Both drawing and hit-testing are constrained to its frame. Always use `PhotoTile(day:)` when a `Day` is available. The pastel cards use `CoverArt(day:)` instead: a user photo still goes through `PhotoTile` in a rounded tile, while a preset draws `FlatCover` straight on the category pastel, as the editor's template picker, share cards, widgets and onboarding do. The bitmap covers these replaced were most of the download and are gone; don't add bitmap artwork back without a reason.

The app icon (晴空日月: a yellow sun held by a white crescent moon on a pale sky, drawn like the flat covers) comes from `python3 scripts/app-icon.py`, which renders it with headless Chrome into `AppIcon.appiconset` — an opaque light icon plus transparent dark and grayscale tinted variants for iOS 18 — and resizes it to the site's `docs/assets/icon-180.png` / `icon-512.png`. Run `bash scripts/og-images.sh` afterwards, since the share images show the icon.

Photo decoding uses ImageIO downsampling before allocating the display bitmap. `PhotoDecodeCache` shares size-specific results using full-content SHA-256 keys, with a 32 MiB `NSCache` cost limit (an eviction hint, not a hard process-memory ceiling). Each `PhotoTile` keeps its photo's digest in a `PhotoDigestMemo` (`@State`, unobserved), so an update that keeps the photo doesn't hash it again; `Data.hasSameBytes` recognises an unchanged photo's shared buffer without reading it. Compact rows use 192/256px thumbnails and category tiles 512px; full covers default to 1600px. List rows pass `decodesAsynchronously: true` to decode uncached photos off the main actor; widgets and `ImageRenderer` exports must keep synchronous decoding, since their tasks never run. Import downsampling and JPEG encoding run off the main actor. Off-main work goes through `@concurrent` functions (`PhotoDecodeCache.decodedInBackground` / `compressedJPEGInBackground`, `DayBackup.load(from:)`) rather than `Task.detached`, and shared caches guard their state with `Mutex`. Pixel limits must not be multiplied by the device screen scale. `RenderingTests.testPhotoImportPixelBudgetAndBenchmark` compares the old renderer path with the new import on the same 12MP fixture.

### Categories

`DayCategory` (`Models/DayCategory.swift`) is the original five-value enum (`.love`, `.family`, `.travel`, `.work`, `.life`) and remains on every `Day` for backwards compat — the widget and older snapshots still decode it. Custom categories layer on top via `CategoryDefinition` (id / name / icon / `colorToken: CategoryColorToken` / `isSystem`), persisted under `categories.v1`. Each `Day` carries `categoryID` (a free-form string for custom categories, or the system enum's raw value) and a `categoryLabel` snapshot of the name at write time.

`DayStore.updateCategory` rewrites the `categoryLabel` on every day that referenced a renamed custom category, including the copies in 最近删除 and 同步保留版本 (restoring a kept version keeps it exactly as it was). `deleteCategory(id:migrateTo:)` requires a migration target and rewrites `categoryID` / `categoryLabel` / `category` on each affected day in one pass, including the copies in 最近删除 and 同步保留版本. System categories (`isSystem == true`) cannot be renamed or deleted; they're merged back into the persisted list on every load via `normalizedCategories(_:)`, so a missing system category in stored JSON is self-healing.

Unknown category IDs and label snapshots survive normalization because cloud days may arrive before their category definitions. Appearance-only category edits do not rewrite days. Settings record their local timestamp immediately, before the debounced cloud push, and a newer accepted remote snapshot cancels that pending push.

### Lunar calendar

`Lunar/` retains the table and conversion semantics from `_design/days-remember/project/lunar.jsx`. `LunarTable.info` is the 1900-2100 packed bitfield, with four words the prototype got wrong corrected to the Hong Kong Observatory tables (`LunarTests.testTableMatchesHongKongObservatory`); immutable cumulative year offsets avoid repeatedly summing it during conversion. `LunarTests` checks all 73,412 supported days and records a 2,000-round-trip benchmark. All formatters live in `Lunar.swift`: `solarToLunar`, `lunarToSolar`, `fmt`, `fmtFull`. The app calendar (`CNDate.calendar`) uses `Asia/Shanghai`, and conversion counts its calendar days rather than elapsed seconds: its midnights aren't UTC+8 midnights during the 1919, 1940s and 1986–1991 daylight saving or before 1901. `SolarTerms.swift` solves the 24 节气 from the truncated VSOP87 series in `VSOP87.swift` (plus nutation, aberration and ΔT), dates them in Beijing time and caches each year; `LunarTests` pins published equinox/solstice instants to within two minutes. Traditional festivals skip leap months and include 除夕.

`DayInfo.compute(_:today:)` (in `Models/DayInfo.swift`) is the recurrence logic. It, `RecentOccurrence.of` and `Milestone.next` memoize per day through `DailyCache`, and `CNDate.startOfDay` keeps the latest boundary, because the feeds ask for every day on each update:

- Non-recurring days → countdown to original date.
- Recurring (Gregorian) → next anniversary in current/next year.
- Recurring **lunar** → search Gregorian years for the first occurrence `≥ today`. `DayInfo.occurrences(of:inGregorianYear:)` is shared with the calendar and checks both adjacent lunar years, preserving January anniversaries and years containing two occurrences. A 三十 recurs on the last day of a 29-day month, as 除夕 does. Gregorian February 29 normalizes to March 1 in non-leap years, through `DayInfo.gregorianAnniversary(of:inYear:)`, which the countdown, the calendar, reminders and whole-year milestones all use.

Days are stored as dates on the app calendar, so a birthday stays on its day anywhere; the device's own time zone decides which day is today and when reminders arrive. `CNDate.appTime(_:)` gives the app-calendar time that reads the same on a clock as a real moment does on the device, and `CNDate.instant(_:)` goes back: `Today.date` is `CNDate.appTime(.now)` in production, notification planning works in app time and asks for that wall-clock time with no time zone (so a reminder follows the device when it travels), pending reminders are read back into app time, and widget entries sit at local midnights (`CNDate.localDayStarts`) and count from `DaysEntry.today`. Lunar dates and solar terms stay in Beijing time, as the Chinese calendar is defined. In DEBUG, `Today.date` reads the `DR_PIN_TODAY` env var: `"1"` pins to `2026-04-23` (the prototype's reference today), or any `yyyy-MM-dd` string pins to that date — useful for date-sensitive test runs. All countdown computations go through `Today.date`, never `Date()` directly.

### Widget extension & shared sources

`DaysRememberWidget/` is an `app-extension` target. `project.yml` shares Models, Lunar, Theme, SharedStorage, PhotoTile and PhotoDecodeCache, fonts, and localization with the app. The widget's own `Assets.xcassets` holds the same flat cover vectors, which `scripts/flat-covers.py` writes. `DayWidgetCard` supplies all three widget sizes and the exact in-app preview layouts. `SelectWidgetDay` uses App Intents for per-widget day selection; leaving it empty selects among the pinned days if any, the nearest upcoming day without a one-year cutoff, or the most recent past day when nothing is ahead. `DaysListWidget` (medium and large, `StaticConfiguration`) lists `WidgetDay.list` — the feed's order, pinned first — through `DayListWidgetCard`, which the gallery previews too, and reads no photos. `NewDayControl` is a Control Center button running the shared `NewDayIntent`. `WidgetDay.resolve` is shared with the in-app preview. A deleted selected day renders an empty state, never an unrelated replacement. The provider reads `categories.v1` (`SharedStorage.loadCategories()`) so a custom category's card keeps its colour, resolved by `CategoryDefinition.colorToken(for:in:)` as the app does, and decodes day metadata only (`SharedStorage.loadLibrary()`) and reads photos just for displayed days (`Library.withPhoto`; none for Lock Screen families), then requests a refresh at the next midnight; the entry date is passed into the card for its countdown. The in-app picker is only a preview; actual instances are configured through the system Edit Widget menu.

Both targets carry the App Group entitlement (`DaysRemember/Resources/DaysRemember.entitlements`, `DaysRememberWidget/DaysRememberWidget.entitlements`). On the simulator the group works without provisioning.

Widget photos use `PhotoTile.maximumPixelSize` (512 for small, 720 otherwise). WidgetKit archives the bitmap itself; resizing its SwiftUI frame does not avoid the image-area limit. Keep the pixel-bound regression test, including Retina image scales, and verify a real Home Screen widget rather than only the in-app gallery.

When changing the data model in `Day.swift` or its persistence format, be aware: the widget reads the same JSON, and CloudKit records carry the same day metadata. `Day.init(from:)` already supplies defaults for every field added after the initial schema (`recurring`, `lunar`, `categoryID`, `categoryLabel`, `coverFocusX/Y`, `reminderOffsets`, `note`, `location`, `pinned`); add new fields via `decodeIfPresent` with a sensible default, or bump `storageKey` / `icloud.*.v1`.

| App Intents | `Intents/`: `DaysUntilIntent` (answers without opening the app), `OpenDayIntent` and `NewDayIntent`, offered by `DaysShortcuts` with phrases translated in `Resources/AppShortcuts.xcstrings` (string sets with `${applicationName}`, `${day}`, `${target}`); `updateAppShortcutParameters()` runs at launch and when the app goes to the background. Intents, the control and the Home Screen quick action (`QuickActions`, reached through `AppDelegate`'s scene delegate) leave a `PendingLink` in shared defaults, and `RootTabView` opens it (`daysremember://new` or `daysremember://day/<id>`) on launch, activation or its notification. `NewDayIntent.swift` and `PendingLink.swift` are compiled into the widget too. |
| TipKit, StoreKit | `Tips/DayMenuTip` points out the long-press menu once; `Tips.configure()` runs in `DaysRememberApp.init`, before any view asks for a tip, and automated launches hide tips; `ReviewPrompt` asks for a rating after the user adds a day, with five days and a week of use, once per version. |

Per-day reminder offsets use `nil` for global settings and `[]` for no day reminders. Times of day are shown with `CNDate.time(hour:minute:)`, in the locale's preferred hour cycle as the time pickers show them (09:00 in Simplified Chinese, 上午9:00 in Traditional Chinese, 9:00 AM in English); day counts use `Text(_:format: .number)` or `.formatted(.number.locale(AppLocalization.locale))`, since a bare `.formatted()` ignores the in-app language. Ordinary reminders and yearly memories share the same time: the day's override, else the global time.

## Conventions

- Commits use [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `feat(scope):`, …). Each integration / discrete change is its own commit.
- Every target builds in the Swift 6 language mode (`SWIFT_VERSION` in `project.yml`), so data races are compile errors. CI runs pushes to `main` on a self-hosted Mac (runner labels `self-hosted, macOS, ARM64`), with the Xcode it has selected (27.1 now); pull requests and other branches, a fork's included, since the repository is public, run on GitHub's `macos-26` with Xcode 26.6 (Swift 6.2), whose Release builds flag some isolation cases Swift 6.4 accepts, and which lacks Xcode 27 APIs. A manual run can tick `self_hosted` to use the self-hosted Mac. UI test classes are `@MainActor`; a teardown that drives the app overrides `tearDown() async throws`, since the synchronous override stays nonisolated.
- `HotPathPerformanceTests` times the work the main screens repeat on every update over a 300-day library and prints `HOTPATH` medians; build with `SWIFT_OPTIMIZATION_LEVEL=-O` for representative numbers, and check machine load first.
- Tests in `DaysRememberTests/` use `@testable import DaysRemember`. The target requires the main module to be built with `-enable-testing` (XcodeGen does this automatically for the test bundle).
- Sample data in `Models/SampleData.swift` is verbatim from `_design/days-remember/project/data.jsx` — keep them in sync if regenerating.
- Validate UI changes with simulator screenshots and the rendering/UI tests, including compact screens and large accessibility text. Controls keep a 44pt tap area inside their label, and a confirmation dialog attaches to the control that opens it (a dialog shared by list rows stays on the list).
- `docs/` is the public product site at https://days.gooday.dev (product, privacy policy and support pages, one per language: Simplified Chinese at the root, the others under `zh-Hant/` and `en/`; the Simplified privacy and support pages forward the old `#zh-Hant` / `#en` section links), deployed by Cloudflare Workers Builds from `main` through `wrangler.jsonc`, and holds the App Store screenshots. Pages live in their own directories (`privacy/index.html`), because the host redirects `.html` URLs; `docs/_redirects` makes those redirects, and the ones that add a trailing slash, permanent (301 instead of the host's 307), so list every new page there. Animation runs only under `html.motion`, which each product page's head script sets unless reduced motion is asked for; it moves only opacity and transforms, `.reveal` marks what animates into view, and every page must read completely without it. The pages show 900 px WebP copies of the App Store screenshots from `docs/assets/screens/`, written by `bash scripts/web-screenshots.sh` (which `scripts/screenshots.sh` runs last; needs `cwebp`). `node --test scripts/site-tests/*.test.mjs` runs site.js against a small fake DOM and checks the styles and markup; the tests live outside `docs/` so they aren't published. `bash scripts/og-images.sh` renders the 1200×630 share images in `docs/assets/og/` from `scripts/og-image.html` and the screenshots with headless Chrome; run it after `scripts/screenshots.sh`. Everything there is published, and its claims must match the app; update the pages when a described feature, setting name or data practice changes. `SettingsView.siteURL` links to it.
